# SwingHunter AI 開発ルール（Git運用）

---

# 1. 目的

本プロジェクトでは、コード・設計書・変更履歴を一貫して管理し、長期的に保守しやすい開発を行う。

実装・設計・ドキュメントを常に一致させ、いつでも過去の状態へ戻れるようにする。

---

# 2. 開発フロー

新機能を追加するときは、必ず以下の順番で進める。

```
① 要件・仕様確認
        ↓
② ロードマップ更新
        ↓
③ ドキュメント更新
        ↓
④ 実装
        ↓
⑤ 動作確認・テスト
        ↓
⑥ Gitコミット
```

設計変更がある場合は、必ずコードより先にドキュメントを更新する。

途中の状態ではコミットせず、「一つの機能が完成し、テストが成功した状態」でコミットする。

---

# 3. コミットするタイミング

以下の場合にコミットを行う。

- 新しい機能が完成した
- バグ修正が完了した
- リファクタリングが完了した
- テストが成功した
- 設計変更が完了した
- ドキュメント更新が完了した

以下の場合はコミットしない。

- 作業途中
- テスト未実施
- 一時的なコード変更
- 動作未確認

---

# 4. コミットメッセージ

コミットメッセージは「何を変更したか」が分かる内容にする。

例

```
Add moving average calculation

Implement volume analysis

Create stock data initialization

Refactor database repository

Update project roadmap

Fix duplicate stock price issue
```

日本語でも問題ないが、内容が一目で分かるように記述する。

---

# 5. バージョン管理方針

SwingHunter AIではフェーズ単位・バージョン単位で管理する。

| Version | 内容 |
|---------|------|
| Ver1.x | Data Layer |
| Ver2.x | 移動平均線・出来高による売買システム完成 |
| Ver3.x | テクニカル分析機能追加 |
| Ver4.x | バックテスト・検証 |
| Ver5.x | UI・通知 |
| Ver6.x | AI分析・自己学習 |

各バージョンには以下のドキュメントを残す。

- 実装内容
- 変更内容
- 設計変更
- 完了条件
- テスト結果

---

# 6. Gitで管理するもの

管理対象

- Pythonコード
- tests
- README.md
- docs配下
- requirements.txt
- 設定ファイル

---

# 7. Gitで管理しないもの

管理対象外

- .venv/
- __pycache__/
- logs/
- data/stock.db
- data/stock_data/
- *.sqlite
- 一時ファイル
- 実行時キャッシュ

これらは .gitignore で除外する。

---

# 8. ドキュメント更新ルール

設計変更があった場合は、コードより先に docs を更新する。

更新対象

- 要件定義書
- ロードマップ
- バージョン履歴
- システム構成
- フォルダ構成
- 分析仕様書

コードとドキュメントは常に一致させる。

---

# 9. テスト方針

新機能を追加したら、必ず tests にテストコードを追加する。

確認項目

- 単体テスト
- データ整合性
- 重複チェック
- エラー処理
- 実運用を想定した動作確認

すべて成功後にコミットする。

---

# 10. 開発ルール

実装はレイヤーごとに行う。

```
Data Layer
      ↓
Indicator Layer
      ↓
Analysis Layer
      ↓
Rule Engine
      ↓
Scoring Engine
      ↓
UI
      ↓
AI
```

各レイヤーが完成したら、

- ドキュメント更新
- テスト
- Gitコミット

を行い、次のレイヤーへ進む。

---

# 11. GitHub運用

GitHubはプロジェクト全体のバックアップとして利用する。

運用方針

- ローカルGitで日常開発
- Verごとの節目でGitHubへPush
- 大きな機能追加後にタグ付け
- リリース単位で履歴を残す

GitHub上でも各バージョンの開発履歴を追跡できる状態を維持する。
