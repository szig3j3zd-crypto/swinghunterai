# 支持線・抵抗線 判定仕様書

---

# 1. 目的

過去の株価から、多くの投資家が意識している価格帯を自動抽出する。

支持線・抵抗線は「1本の線」ではなく、**価格帯（ゾーン）**として扱う。

検出対象期間（日足1年／週足3年／月足7年）は entry_signal_spec.md 3章のデフォルト値に従う。

---

# 2. 高値・安値候補（スイングポイント）の抽出

以下を満たすローソク足を高値候補とする。

- 前後2〜3本より高い（初期値: 前後2本、config変更可）
- 例: High(i) > High(i-1), High(i-2), High(i+1), High(i+2)

安値も同様の考え方で、前後2〜3本より安い足を安値候補とする。

---

# 3. 価格帯（ゾーン）へのクラスタリング

逐次クラスタリング方式を採用する。

- 候補点を価格順にソートする
- 新しい候補点が、現在の帯の平均値との差 ±2% 以内なら同じ帯に追加し、帯の平均値を再計算する
- ±2%を超えたら新しい帯として扱う
- 帯の代表価格（ライン価格）は、帯内の全候補点の平均値とする

支持線・抵抗線をまたいで同じロジックを使う。

---

# 4. ラインの採用条件（形成条件）

以下をすべて満たした帯のみを「有効なライン」として採用する。

- タッチ回数: 3回以上
- 期間: 最初のタッチから最後のタッチまで一定期間以上離れていること
  - デフォルト: 日足3ヶ月／週足6ヶ月／月足1年（検出対象期間より短い、独立したパラメータ。config変更可）

この採用条件は、6章のエントリー候補カウント（反発1・2発目）とは**別のレイヤーの判定**である。

- タッチ回数（本章）: 支持線・抵抗線という「ライン自体」が実在するかどうかの判定基準
- 反発回数（entry_signal_spec.md 6章）: ラインが有効になった後、そのラインで発生する半分シグナルのうち、エントリー候補にするかどうかの判定基準

---

# 5. 出来高による信頼度加点

ライン付近の出来高が平均以上であれば信頼度を加点する。

- 例: 平均出来高の1.5倍以上で加点（しきい値はconfig変更可）

---

# 6. ブレイク判定・ライン終了（統一基準）

- 終値がライン±1%を超えて推移し、**3営業日連続**でライン外側を維持したら正式ブレイクと判定し、同時にラインを終了とする
- 3営業日未満で内側に戻った場合はダマシとして扱い、ライン終了とはしない（タッチ回数・エントリー候補反発回数もリセットしない）

ブレイク確定とライン終了は同一の事象として扱い、判定基準を統一する。

---

# 7. リセット条件（優先順位順）

| 優先度 | 条件 | リセット | 備考 |
|--------|------|----------|------|
| ★★★★★ | 終値でラインを明確に突破し、3営業日維持 | する | 6章のブレイク判定と同一基準 |
| ★★★★☆ | 株式分割・株式併合 | する | 自動検知は行わない。ニュース等の外部情報で判断する必要があり、Phase2では未対応（12章参照） |
| ★★★★☆ | ラインから20%以上乖離 | する | 直近終値とライン価格との乖離で判定 |
| ★★★☆☆ | 最終タッチから365日以上経過（ラインの有効期限） | する | 全時間足で共通の日数を使う（config: SR_INACTIVITY_RESET_DAYS） |
| ★★☆☆☆ | 上位足で完全にトレンド転換 | する | Ver3.2（水平ラインの高度化）で対応。Phase2では対象外 |
| ★☆☆☆☆ | 一時的なヒゲ抜け・3営業日未満の突破 | しない | 6章のダマシ判定と同一基準 |

## ラインの引き継ぎ（役割転換）方式 ※Ver3.0以降

理想的には、リセット時は「反発回数を完全に0に戻す」のではなく、**旧ラインを終了し、同じ価格帯に新しいラインを役割反転で作成する（世代管理）**方式が望ましい。

例:
- 抵抗線3,000円で5回反発 → 明確に上抜け（3営業日維持）
- 旧ライン（Line ID 1、抵抗線、3,000円、タッチ5回）は終了として記録
- 新ライン（Line ID 2、支持線、3,000円、タッチ0回）を作成

**Ver2.0では世代管理は行わない。** 検出期間内の全タッチをまとめて1つの帯として扱い、ブレイク後も同じラインとして扱う（`_is_broken`が真の帯はそもそも候補から除外されるのみ）。理由:

- 実装がシンプルで済み、処理速度も速い
- Ver2.0はまずスクリーニング用途として十分な精度があればよい
- ブレイク後に再度同じ価格帯で反応するケースは稀であり、世代を分けなくても実用上の影響は小さい

世代管理はVer3.0以降で追加する。

# 8. エントリー候補としての反発カウント（廃止・Rule Engineでは未使用）

※ 2026-08、entry_signal_spec.mdをモジュール化改訂した際に旧パターンA（支持線付近の
半分シグナル）を廃止したため、本章の内容はRule Engine（`rules/entry_rule.py`）では
使用しなくなった。支持線・抵抗線検出自体（1〜7章）は、チャートへの手動線描画など
Rule Engine外の用途では引き続き利用する。反発回数のカウント方式（5営業日以内マージ・
最大2発まで）は、entry_signal_spec.md 5章の反発モジュールが`rules/bounce_count.py`を
そのまま流用している（支持線・抵抗線には依存しない形に変更済み）。

以下は旧仕様の記録として残す。

## 有効化日

- ラインの「有効化日」は、4章の採用条件（タッチ回数3回以上）を満たした時点、つまり**3回目のタッチが発生した日**とする
- 実装上は `detect_support_lines` / `detect_resistance_lines` が返す各ラインの `valid_since_date` に対応する

## カウント対象

- 有効化日以降に発生する半分シグナルのみを対象とする（有効化前、タッチ1〜2回目の間に発生した半分シグナルはエントリー候補にしない）
- 有効化日以降の半分シグナルのうち、1回目・2回目のみをエントリー候補とする（entry_signal_spec.md 6章）。3回目以降は候補から除外する
- Ver2.0では世代管理を行わないため、この反発回数は「参考値」として扱う（ラインがブレイクして役割転換した場合でも同じラインの延長としてカウントする）

## 近接する反発のまとめ方

- 半分シグナルの発生日が**5営業日以内**であれば、同一の反発としてまとめる（複数日にまたがる細かい上下動を1回の反発として扱うため）
- 5営業日を超えて離れていれば、別の反発としてカウントする
- config: `BOUNCE_MERGE_WITHIN_DAYS`（デフォルト5）、`MAX_ENTRY_BOUNCES`（デフォルト2）

## パターンB（20日線ベース）のカウント区間

- 支持線・抵抗線を伴わないパターンB（20日線付近での半分シグナル）は、`is_long_trend` / `is_short_trend` が連続してTrueである期間（トレンド開始日〜直近日）を対象に、同様のルールで反発をカウントする
- トレンドが終了（Trueが途切れる）した時点で、次のトレンドではカウントをリセットする

## 実装

- `analysis/ma_trend.py` の `get_current_trend_period` でトレンド開始日を取得する
- `rules/bounce_count.py` の `get_bounce_number` / `is_entry_candidate` で反発のグループ化・エントリー候補判定を行う

# 10. データ層への影響

- 支持線・抵抗線の検出には、当初の初回取得期間（約3年）では月足7年・週足3年のデフォルト値を満たせない
- **対応済み**: 東証プライム全銘柄（1,559銘柄）とTOPIX Core30+Large70（大型株100銘柄）について、10年分（当初計画の7年より長い）へ延長取得を実施した（1,461/1,462銘柄成功、失敗1銘柄: 8303）
- それ以外の市場（スタンダード・グロース）の銘柄は約3年分のまま。月足・週足のライン検出精度はその期間分に制限される。プライム市場以外も対象にする場合は追加取得が必要

---

# 11. 未確定・将来課題

- 株式分割・株式併合の自動検知は行わない。ニュース等の外部情報での対応が必要（対応方法は将来検討）
- 上位足トレンド転換によるリセットはVer3.2で対応
- 信頼度スコアの正規化方法とScoring Engineへの統合方法はVer2.3で確定する
- ラインの世代管理（7章「役割転換方式」）はVer3.0以降で対応する。Ver2.0の反発回数は参考値である
