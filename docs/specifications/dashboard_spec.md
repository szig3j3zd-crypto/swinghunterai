# ダッシュボード仕様書（Streamlit UI）

---

# 1. 概要

`ui/dashboard.py`（`streamlit run ui/dashboard.py` で起動）。

「今日の売買候補を見る」「個別銘柄を調べる」「売買記録・監視銘柄を管理する」の3つを
1つの画面で行えるようにしたダッシュボード。サイドバーの設定は全タブ共通。

画面構成:

- サイドバー: 個別銘柄検索・方向・時間足・採用指数・フィルタ・スキャン実行ボタン
- メイン: 「スキャン」「売買銘柄」「監視銘柄」の3タブ

サイドバーの「候補を更新」を押すと、現在どのタブを表示していても「スキャン」タブへ
自動で切り替え、ページの一番上までスクロールする（2026-08-23追加）。
`st.tabs(..., key="active_tab", on_change="rerun")`とし、スキャン実行時に
`st.session_state["active_tab"] = "スキャン"`を書き換えることで実現する
（`key`・`on_change="rerun"`を指定すると`st.session_state[key]`経由でアクティブな
タブを読み書きできる。ユーザーが手動でタブを切り替えた場合はその選択がそのまま
維持され、スキャン実行時のみ上書きする。売買銘柄・監視銘柄タブでチェックボックスを
選択した場合はタブが切り替わらない＝そのタブに留まる。3.1節・5章・6章参照）。

（開発メモ、2026-08-23: `st.tabs(..., key=..., on_change="rerun")`は一度、
タブ・見出しの二重表示という描画崩れを引き起こし撤回したことがある。原因は
`st.tabs()`自体ではなく、その直前で呼んでいた`ui.dashboard._render_scroll_if_needed()`
がスクロール不要な回は要素ごと描画をスキップしており、st.tabs()がキーの無い
ウィジェットとして位置ベースで再識別されてしまっていたこと。呼び出し自体を
毎回安定させたことで解消し、タブ制御を再度有効にしている。3.1節参照）

# 2. サイドバー

## 2.1 個別銘柄検索

`st.selectbox`（"コード 銘柄名" 形式のラベルで部分一致検索）で、東証プライム・
スタンダード・グロースの全アクティブ銘柄から1件選べる。選択すると、スキャン結果の
有無に関わらずその銘柄の判定結果とチャートを表示する（4章）。

## 2.2 方向・時間足

- 方向: ロング（買い） / ショート（売り）
- 時間足: 日足 / 週足 / 月足（週足・月足は`indicators/resample.py`で日足データを
  リサンプルして判定。月足は必要な行数（`min_history`既定値100本＝約8年強）に
  満たない銘柄が多いため、日足・週足に比べて評価できる銘柄が少なくなる）

## 2.3 採用指数（対象銘柄の絞り込み）

`st.multiselect`。複数選択すると、選択した指数の銘柄を**和集合**（コード重複除去）で
まとめて対象にする。デフォルトは「日経225」「JPX日経400」の2つ（2026-08-23変更。
以前は未選択がデフォルトだった）。1つも選択せずにスキャンを実行するとエラー
メッセージを表示して中断する（この挙動自体は変更なし）。

| 選択肢 | 実装（`service/screening_service.py`） |
|---|---|
| 東証プライム全体 | `get_prime_stocks()` |
| 日経225 | `get_nikkei225_stocks()`（`stock_master.nikkei225`列） |
| JPX日経400 | `get_jpx400_stocks()`（`stock_master.jpx400`列） |

日経225・JPX400のデータは`scripts/update_stock_master.py`が
`data/stock_data/master/{nikkei225,jpx400}.csv`を読み込んでDBへ反映する
（nikkei225.csvはヘッダー無し・1列のコード一覧形式）。

## 2.3.1 判断基準（モジュール選択）

`st.multiselect`。entry_signal_spec.md 3〜8章のモジュール（並び順・ゴールデンクロス・
完全ゴールデンクロス・反発・並走上昇・半分シグナル）から使用するものを選び、選択した
モジュールを常にAND結合して候補を判定する（`service/screening_service.py` の
`DEFAULT_MODULES` = 並び順のみが初期選択）。1つも選択せずにスキャンを実行した場合は、
Rule Engineでの判定を行わず、出来高・株価フィルタのみを通過した銘柄をコード・銘柄名・
株価だけの一覧として表示する（3.1.1参照。候補一覧のような判定理由・スコアは持たない）。
採用指数（2.3節）は引き続き1つ以上の選択が必須で、未選択のままスキャンした場合のみ
エラーメッセージを表示して中断する。

「並び順」を選択した場合のみ、3本版（5>20>60）/3本版（5>20>100、デフォルト）/2本版
（5>20のみ）を選ぶラジオボタンを表示する（`ma_mode`。2本版では60日線・100日線フィルタ
も解除される）。

方向（2.2節）がショートの場合、モジュール名自体は共通（内部的には表裏の判定ロジックを
使う）だが、候補一覧・銘柄詳細の「判定理由」表示ではゴールデンクロス→デッドクロス、
完全ゴールデンクロス→完全デッドクロス、並走上昇→並走下降のようにラベルだけ変える
（`service/screening_service.py` の `format_reason`/`_module_label`）。

## 2.4 フィルタ

出来高・株価（下限/上限）・時価総額（下限）を任意に変更できる。すべて「0で無効」。

- 出来高・株価フィルタは`rules/screening_filters.py`、エントリー判定
  （`rules/entry_rule.py` の `evaluate_entry`）内で適用される
- 時価総額フィルタは、DBに時価総額を保存していないため、**他の条件を通過した
  候補にのみ**Yahoo Finance（`data/market_cap_reader.py`）へライブ問い合わせして
  絞り込む（`service/screening_service.py` の `_filter_by_market_cap`）。全銘柄には
  適用しないため、スキャン全体の速度への影響は小さい

「0で無効」の実現方法: `None`を渡すとconfig既定値にフォールバックしてしまうため、
下限は`0`、上限は`float("inf")`という「フィルタ関数がそのまま『制約なし』と
解釈できる値」を明示的に渡す（`rules/screening_filters.py`参照）。

# 3. スキャンタブ

## 3.1 候補一覧

サイドバーの「候補を更新」を押すと、`service.screening_service.get_today_scan_results()`
で選択中の採用指数・方向・時間足・フィルタに基づき候補・監視銘柄候補（3.1.1参照）を
まとめて抽出し、候補一覧はスコア降順の表で表示する（コード・銘柄名・スコア・判定理由・
株価・損切価格・利確価格・リスクリワード比）。候補・監視銘柄候補は同じ全銘柄スキャンで
まとめて仕分けられる（`get_today_candidates()`・`get_today_watchlist()`を個別に呼ぶ
実装だと全銘柄スキャンが2回走ってしまうため、両方必要な場面ではこの1回スキャン版を使う）。

候補が1件以上ある場合、表の直前に見出し「エントリー候補」を表示する（2026-08-23追加。
監視銘柄候補側の見出し「監視銘柄候補」との視覚的な対比のため）。黄色（`#FFC107`）で
強調表示する（`st.markdown(..., unsafe_allow_html=True)`。`st.caption`は文字色を
指定できないため使わない）。

候補一覧・監視銘柄候補一覧（3.1.1）はどちらも、既に保有中（未決済）の売買銘柄の
銘柄コードを除外する（方向は問わない。同じ銘柄をロング・ショート両方で保有している
場合も除外対象。決算済みのトレードは除外しない＝再度候補として出てよい）。

既に監視銘柄として登録済みの銘柄コードは、候補一覧・監視銘柄候補一覧のどちらからも
除外しない（2026-08-23改訂。当初は監視銘柄候補一覧のみ除外をやめたが、
「候補一覧も同じように表示してほしい」との追加要望を受けて候補一覧も揃えた）。
該当行は「備考」列（候補一覧）・「状況」列の先頭（監視銘柄候補一覧）に
`監視銘柄登録済み`の目印を付け、行全体をグレー表示（`ui.dashboard.
_style_already_watchlisted_rows()`、pandas Styler経由。文字色＋斜体だけでなく
背景色（`#ececec`）も付ける。2026-08-29改訂。文字色のみでは選択可能な行との
違いが分かりにくく、クリックしても無反応に見えるだけで「なぜチャートが
開かないのか」気づけない不具合報告があったため）にする。ただし選択自体は
ブロックしない（2026-08-30改訂。以前は`_on_candidate_table_select`・
`_on_watch_candidate_table_select`が`is_already_watchlisted`の行の選択
イベントを無視し、選択してもチャートが開かないようにしていたが、
「グレー表示は登録済みであることが分かればよく、チャート確認までブロック
する必要はない」との要望を受けて選択のブロックをやめた。グレー表示自体は
維持する）。表下のキャプションも「グレー表示の行は既に監視銘柄に登録済み
です（選択してチャートは確認できます）」に変更した（同日）。

行は選択可能（`st.dataframe(..., on_select=..., selection_mode="single-row")`）。
行を選択すると、その銘柄の判定結果とチャートを4章の位置に表示し、「株価チャート」の
見出し（4.2節）がビューポート上端に来るまで自動でスクロールする（2026-08-23追加。
`ui.dashboard._render_scroll_if_needed()`。表の下の方の行を選択すると
チャートが表示されたことに気づけないため。見出しが見つからない場合はメイン
コンテンツの先頭までスクロールするフォールバックを持つ。売買銘柄・監視銘柄タブでの
選択でも同様にスクロールする。3.2節参照）。サイドバーの「候補を更新」を押した
場合は、これとは別にページの一番上までスクロールする
（`st.session_state["scroll_to_page_top"]`）。

`_render_scroll_if_needed()`は`st.tabs()`の直前で、スクロール不要な場合も含めて
毎回同じ形で呼ぶ（`st.components.v1.html()`の呼び出し自体を条件分岐しない）。
呼び出しの有無を再実行のたびに変えると、直後の`st.tabs()`がキーの無い
ウィジェットとして位置ベースで再識別されてしまい、売買銘柄・監視銘柄タブで
銘柄をチェックするたびに選択中のタブが「スキャン」へリセットされてしまう
不具合があったため（2026-08-23発見・修正）。

候補一覧・監視銘柄候補一覧（3.1.1）は別々の`st.dataframe`ウィジェットのため、
Streamlit側は互いの選択状態を関知しない。そのままだと片方の表で行を選択した後に
もう片方の表でも行を選択すると、両方の表でチェックが入ったまま残ってしまう
（2026-08-23、不具合として発見・修正）。そのため、一方の表で行を選択した
コールバック内で、もう一方の表専用の`*_selection_version`（`ui.dashboard.
_on_candidate_table_select`・`_on_watch_candidate_table_select`参照）を
インクリメントし、そちらの表の`key`を変えることで新しい（選択状態の無い）
ウィジェットとして扱わせる。結果として、常にどちらか一方の表の1行だけが
選択された状態になる。

新しいスキャンを実行すると、選択状態・チャート表示はリセットされる
（`scan_version`をインクリメントし、両方の表の`key`に含めることで
Streamlit側に新しいウィジェットとして扱わせる）。

## 3.1.1 監視銘柄候補

反発モジュール（entry_signal_spec.md 6章）・MA60/100接近ウォッチモジュール
（entry_signal_spec.md 14章）・並び順モジュールの監視銘柄候補判定（entry_signal_spec.md
15章）は、判定ロジックこそ別物だがどちらも「エントリー候補にはまだ届かないが、
監視する価値がある状態」を拾うという位置づけは同じなため、候補一覧の下に
**1つの表「監視銘柄候補」**としてまとめて表示する（2026-08-22改訂で反発・
MA60/100接近を統合、2026-08-23改訂で並び順を追加）。

- 表示は、候補一覧（エントリー候補）と同じ**AND結合**（`service.screening_service.
  _is_merged_watch_candidate()`）。反発・MA60/100接近・並び順のうち選択中の
  ものを**すべて**満たす銘柄だけを監視銘柄候補にする（2026-08-23改訂。
  以前はいずれか1つ満たせば表示するOR結合だったが、「全て満たす銘柄に絞って
  ほしい」との要望を受けて変更した）。反発・MA60/100接近・並び順のいずれか
  1つでも選択していれば表自体は表示する（すべて未選択なら表自体を表示しない）
- 監視銘柄候補として表示される銘柄は、選択中の監視系モジュールすべてに
  該当しているため、「状況」列には該当する基準をすべて（`反発: ...`
  `MA60/100接近: ...` `並び順: ...`のように基準名を頭につけて）列挙する
  （選択したモジュールが1つだけの場合はその基準のみ表示する）
- 候補一覧と同じ行選択の仕組みを再利用しており、行を選択すると同じくチャートと
  状況（該当するすべての基準）を表示する
- 該当銘柄が0件の場合は「該当銘柄はありません」と表示する
- 既に監視銘柄として登録済みの銘柄も一覧から除外せず含める（2026-08-23追加）。
  ただし区別できるよう、該当行は「状況」列の先頭に`[監視銘柄登録済み]`を付け、
  行全体をグレー表示にする（`ui.dashboard._style_already_watchlisted_rows()`、
  pandas Styler経由。3.1節参照）。行クリックによるチャート表示・銘柄詳細表示は
  ブロックしない（2026-08-30改訂。3.1節参照。以前はグレー表示の行の選択自体を
  無効化していた）

MA60/100接近ウォッチモジュール、および並び順モジュールの監視銘柄候補判定は、
候補一覧（エントリー候補）のAND結合には一切影響しない（選択しても候補一覧の
絞り込み条件は変化しない。並び順モジュール自体のエントリー候補への寄与は
従来通り）。監視銘柄候補側のAND結合は、あくまで監視系モジュール同士の間だけで
行う独立した仕組み。

## 3.2 売買銘柄・監視銘柄への追加

候補一覧の候補、または個別銘柄検索の結果（**エントリー候補かどうかを問わない**。
手動で売買記録・監視したいだけの場合もあるため）から銘柄を選び、

- 売買銘柄として追加: 取引日・購入株価（デフォルトは現在株価）・株数・決算株価
  （0のままなら未決済）を入力して登録
- 監視銘柄として追加: ボタン1つで登録（方向のみ引き継ぐ）
- どちらも、その銘柄を評価したときの時間足（サイドバーの「時間足」）を
  一緒に記録する（候補一覧・個別銘柄検索いずれも`service.screening_service`の
  候補/評価結果dictに`timeframe`キーとして含まれる）。売買銘柄・監視銘柄タブ
  では、この時間足は表内の列として区別するのみで、表自体は日足・週足を
  まとめた1つの表になる（5章・6章参照）

# 4. 個別銘柄検索・銘柄詳細（チャート）

個別銘柄検索、または候補一覧の行選択のどちらでフォーカスした銘柄でも、
同じ位置（候補一覧の直前）に同じ形式で結果を表示する
（`_render_focus_block`、`focus_mode`／`focus_candidate`セッション状態で管理）。

候補一覧を更新すると個別銘柄検索側のフォーカスは消え、逆に個別銘柄検索を
操作すると候補選択側のフォーカスに優先する（検索ボックスの`on_change`で
`focus_mode="search"`をセットし、候補一覧側は選択イベントのコールバックでのみ
`focus_mode="candidate"`を書き換える。単純に選択状態を毎回読み直す方式だと、
ウィジェットの選択状態が残り続けて他方の操作を上書きしてしまうため）。

## 4.1 判定結果

見出し（`銘柄詳細: {コード} {銘柄名}`）の直後はステータスメッセージのみを
表示し、詳細テーブルは挟まずすぐ4.2節のチャートを表示する（2026-08-29改訂。
以前はエントリー候補の場合のみコード・銘柄名・スコア等の1行詳細テーブルを
挟んでいたが、売買銘柄・監視銘柄タブ（銘柄名の見出し→すぐチャート）と
見え方が揃わず、自動スクロール（3.1節`scroll_to_chart`）で見出しを画面上端に
持ってきても、その直後に見慣れない詳細テーブルが挟まる形になり「チャートに
移動していないように見える」という問い合わせにつながったため削除した。
詳細情報自体は候補一覧の表に既に出ている）。ステータスメッセージは3パターン。

- **エントリー候補**（`is_entry_candidate=True`）: `st.success`で
  「本日のエントリー候補です」と表示する
- **監視銘柄**（`is_watch_candidate=True`。反発モジュールでMA20を下回った/ショートなら
  上回った状態）: `st.warning`で「監視銘柄です」と現在の株価を表示する。回復すれば
  翌日以降の再スキャンでエントリー候補に昇格する
- それ以外の見送り: 見送り理由（`SKIP_REASON_LABELS`で日本語化）と現在の株価を表示する

## 4.2 チャート（`ui/chart.py`）

`service.screening_service.get_stock_chart_data()`で取得したOHLCV＋移動平均
（sma3/5/7/10/20/60/100）をPlotlyのローソク足＋出来高サブプロットで表示する。

チャート部分の描画自体は`ui.dashboard._render_chart_block(code, chart_timeframe,
key_prefix)`として切り出してあり、スキャンタブ（`_render_focus_block`内、
`key_prefix="scan"`）だけでなく、売買銘柄タブ・監視銘柄タブで銘柄を選択した
ときのチャート表示（5章・6章、それぞれ`key_prefix="trades"`／`"watchlist"`）
からも共通で呼び出す。`key_prefix`は、同じ実行内で複数タブのチャートが
同時に構築されてもStreamlitウィジェットの`key`が衝突しないための区別用で、
表示設定（チェックボックス・表示期間・表示幅）もタブごとに独立して覚える。

- 表示切替: ローソク足・3日線・5日線・7日線・10日線・20日線・60日線・100日線・
  出来高・詳細情報（ホバー表示のON/OFF）のチェックボックス。3日線・7日線・
  10日線は参考表示用（並び順・ゴールデンクロス等の判定ロジックでは使用
  しない）で初期状態は非表示。5日線・20日線・60日線・100日線は初期状態で
  表示（日足・週足・月足いずれの時間足でも、列名・ラベルはsma5/sma20等の
  ままで固定しており、時間足に応じて「5週線」「5ヶ月線」のようには変えない）
- 表示期間・表示幅: 2つのプルダウンで別々に指定する
  - 表示期間: チャート上を横スクロールして見られる範囲全体。1ヶ月・3ヶ月・
    6ヶ月・1〜10年（1年刻み）。表示期間より古いデータはチャートに渡さない
    （`chart_df[chart_df["date"] >= period_start]`）ため、横スクロールで
    移動できる範囲そのものが表示期間で区切られる。日足/週足/月足を
    切り替えても値を変えない（`chart_period_pref_{key_prefix}`、
    デフォルト`CHART_PERIOD_DEFAULT`="5年"）
  - チャート表示幅: 画面に一度に表示する幅。3〜11ヶ月（1ヶ月刻み）・
    1〜5年（1年刻み）。表示期間より広い幅を選んだ場合は表示期間の開始日で
    クランプする
  - 表示幅は「ローソク足の本数」を時間足に依存しない基準として保持し
    （`chart_display_width_bar_target_{key_prefix}`、日足の
    `CHART_DISPLAY_WIDTH_DEFAULT`="6ヶ月"相当の本数がデフォルト）、
    プルダウンに表示するラベル自体は時間足ごとに、その本数に最も近い
    ものを選び直す（`ui.dashboard._closest_width_label_for_bar_count()`。
    2026-08-30追加）。同じ「6ヶ月」でも日足は営業日換算で約130本、
    週足は約26本、月足は約6本と表示本数が大きく異なり、ローソク足の
    見た目の太さが時間足を切り替えるたびに揃わなかったため、本数基準に
    変更した。本数の換算は暦日ベースの概算（`CHART_BARS_PER_CALENDAR_DAY`。
    日足は営業日率5/7、週足は1/7、月足は1/30.4368）で、実際の本数計算
    自体は表示期間内の実データを数えて行う。月足は選択肢の上限が5年
    （60本）のため、日足換算で約130本相当を指定していても本数は揃わず、
    最も近い選択肢（5年）にとどまる（ラベルが示す暦期間と実際の本数の
    対応がずれる点は許容する）
  - この本数基準での自動選択により、日足/週足/月足を切り替えるたびに
    表示幅のプルダウンの表示値自体は変わりうる（以前は表示期間と同様
    時間足を問わず同じラベルを維持していたが、本数を揃えるために
    ラベル表示を時間足ごとに変える方式に変更した。値の実体（本数）は
    引き続き時間足を横断して共有される単一の設定のため、表示期間側で
    過去に問題になった「時間足ごとに独立した状態を持たせたことによる
    表示位置復元の不安定化」は再発しない）
- Streamlitが描画する初期表示は、表示幅ぶんのデータに価格軸・出来高軸の
  レンジを自動でフィットさせたもの（`ui.chart.compute_visible_window`）。
  表示期間全体分のレンジのまま表示するとローソク足が潰れて見えなくなるため
- 表示幅を保ったまま表示期間の範囲内を左右にスクロールする方法は3通り
  あり、どちらもStreamlitの再実行を伴わずブラウザ側（Plotly.js）だけで
  完結するため滑らかに動く。いずれも`ui.chart.build_scroll_sync_script`
  （`st.components.v1.html`で`st.plotly_chart`の直後に埋め込む
  JavaScript）が実現している
  - 出来高チャートの下にあるスクロールバー（トラック＋つまみのシンプルな
    見た目）のつまみをドラッグする、またはトラックの余白をクリックして
    ジャンプする。Plotly標準のレンジスライダー（`rangeslider_visible`）も
    検討したが、トラック内に全期間のミニチャートを描画してしまい見た目が
    煩雑になる（ユーザー確認済み）ため、独自に描画する方式にした
    - つまみの位置・幅は、現在のPlotlyのxaxis.rangeが表示期間全体の
      どこに当たるかから毎回計算し直す（固定のセッション状態は持たない）
    - つまみ・トラックへの実際のクリックは、iframe自身のdocumentで発生する
      イベントであり親ページのdocumentへは伝播しない（iframeは別ドキュメント
      であり、中で起きたmousedown等が親にbubbleすることはないため）。その
      ため、ドラッグ中のmousemove/mouseupを含めてすべてこのiframe自身の
      要素・documentで受け取る（横方向にどれだけ動いても、iframeの高さの
      範囲内でカーソルが動いている限りイベントは発火し続ける）
    - iframe内をクリックするとブラウザの仕様上フォーカスがそのiframe側に
      移り、以後キーボードイベント（矢印キー）は親ページの`document`へ
      届かなくなる（キーイベントはフォーカスのあるドキュメントへ配送される
      ため）。そのため、つまみのドラッグ終了時・トラッククリック時に
      `window.parent.focus()`を呼び、フォーカスを親ページへ戻して矢印キーの
      スクロールを引き続き使えるようにしている
  - チャート上をマウスでドラッグする（`dragmode="pan"`）
  - チャート・出来高チャートにマウスを乗せた状態で左右の矢印キーを押すと
    ローソク足1本分ずつ移動する。表示期間内の全ローソク足の日付をこの
    scriptへ渡しておき、その実データを1件ずつ辿ることで営業日以外
    （土日・祝日等）は自動的に読み飛ばされる。矢印キーのkeydownリスナーと
    Plotlyのplotly_relayoutイベントリスナーは、親ページ（`window.parent.
    document`）・チャートdivという長寿命の対象に登録するため、チャートの
    再描画のたびにこのscriptも作り直される以上、古いリスナー（それを
    作ったiframeがDOMから削除されると実行コンテキストごと無効になり
    反応しなくなる）を使い回さず毎回明示的に張り替える
  - スキャン/売買銘柄/監視銘柄タブが同時にチャートを表示しているケースが
    あるため、矢印キーが実際にどのチャートを動かすかは「直前にマウスが
    乗っていたチャート」で決める（本数・現在位置などの状態は各チャートの
    DOM要素に直接持たせ、チャート同士が干渉しないようにする）
  - 表示範囲が変わるたびに（スクロールバー・ドラッグ・矢印キーの
    いずれが原因でも）、Plotlyの`plotly_relayout`イベントを起点に、
    その範囲内の高値・安値・出来高から価格軸・出来高軸のレンジを自動で
    再フィットし、あわせてスクロールバーのつまみの位置・幅も更新する
    （`compute_visible_window`と同じ計算をブラウザ側で再現）
  - いずれの方法でスクロールしても、他の操作（チェックボックス切替等）で
    再読み込みされると位置は消える（「既知の制限」参照）。表示位置を
    Streamlit側のセッション状態と同期する仕組みは持たない（かつては
    独自の`st.slider`を用意し、値をStreamlitへ同期する実装を試みたが、
    その分Streamlitの再実行が挟まって滑らかさが失われるため撤回した）
  - `_get_cached_chart_data`（`@st.cache_data(ttl=3600)`）でDB読込・
    移動平均/出来高計算の結果をキャッシュしている。表示期間・表示幅・
    チェックボックスの切替のたびにStreamlitの再実行は発生するため、
    そのたびにDB再読込・指標再計算をやり直すと重くなるため
- 表示切替チェックボックス・表示期間・表示幅の選択状態は、対象銘柄が
  一度も描画されない実行（候補一覧の更新直後など）を挟んでも維持される
  （`ui.dashboard`の`chart_pref_*`／`chart_period_pref_*`／
  `chart_display_width_pref_*`セッション状態。ウィジェット自身の`key`は
  Streamlitの仕様上そのようなrunを挟むと破棄されるため、独立した
  セッション状態で手動管理する）
- 色: 陽線=赤、陰線=青（日本の慣例）、3日線=黄緑、5日線=黄、7日線=ピンク、
  10日線=紫、20日線=赤、60日線=青、100日線=茶、出来高バーは陽線陰線を
  区別せず全て黄
- 土日・祝日などデータの無い日はx軸から除外し（`ui.chart._compute_date_rangebreaks`）、
  ローソク足・出来高バーが空白なく詰めて表示される
- 日付軸ラベル: 表示幅が3ヶ月なら「月/日」、それ以外（4ヶ月〜5年）
  なら「年/月」形式（`build_price_chart`の`tick_format`引数、
  `ui.dashboard`が選択中の表示幅から決定して渡す）
- 高値・安値・始値・終値は、チェックボックス行とチャートの間に専用の行
  として表示する（常時表示、最新足の値）。以前はPlotly側の注釈
  （`fig.add_annotation`）として凡例の右隣に埋め込んでいたが、移動平均線の
  表示切替が増えて凡例が伸びると注釈と重なって読めなくなるため、
  Streamlit側の独立した要素（`ui.dashboard._render_chart_block`内の
  `st.markdown`）に変更した
- ホバー時の詳細情報: カーソルを合わせると、高値・安値・始値・終値・
  （表示中の）3日線/5日線/7日線/10日線/20日線/60日線/100日線・出来高を1つのボックスにまとめて日本語
  ラベルで表示する（`ui.chart._build_hover_text`）。ローソク足・移動平均線・
  出来高バーそれぞれの個別ホバーは無効化し（`hoverinfo="skip"`）、透明な
  補助トレース（価格側・出来高側それぞれに重ねて配置）にホバー内容を
  まとめることで、どちらのサブプロットにカーソルを合わせても同じ内容が
  出るようにしている
  - `hovermode="x"`（x座標のみで最近傍点を判定）を使用。`"closest"`
    （x・y双方の距離で判定）だとカーソルが価格ラインから縦に離れた際に、
    縦の点線（`spikesnap="cursor"`でカーソルのx座標にそのまま追従）とは
    別の日付の情報を表示してしまうため
  - 「詳細情報」チェックボックスをOFFにすると`hovermode=False`になり、
    ホバーボックス・縦の点線とも非表示になる
- 縦の点線（スパイクライン）はホバー中のサブプロット側にのみ表示される
  （`spikemode="across"`でサブプロットを跨いで伸ばす設定を試みたが、
  Streamlit同梱のPlotly.jsでは十分に機能しなかった）
- チャート上でのマウスカーソルは、Plotly標準の十字（crosshair）ではなく
  矢印のまま維持する（CSSで`.nsewdrag`のcursorスタイルを上書き、
  `ui.chart.PLOTLY_CURSOR_OVERRIDE_CSS`を`ui.dashboard`が起動時に注入）。
  ドラッグでのパン・ズーム操作自体には影響しない
- モードバーのアイコン説明は日本語化（`ui.chart.PLOTLY_JA_LOCALE`。Plotly公式の
  日本語ロケールファイルを読み込む手段が無いため、英語→日本語の対訳辞書を
  `config.locales`に直接渡している）
- モードバーの「直線を描画」で支持線・抵抗線を描画できる。描いた線はクリックで
  選択→端点ドラッグで編集、「選択した図形を削除」アイコンまたはDeleteキーで削除

### 既知の制限

- 手動でのスクロール（レンジスライダー・ドラッグいずれも）・ズーム・
  描画した線は、**他の操作（チェックボックス切替等）で再読み込みされると
  消える**。Plotly標準の`uirevision`とStreamlitの`key`を組み合わせる方法を
  試したが、`st.plotly_chart`では効かなかった（Streamlit側の制限と
  考えられる）。表示期間・表示幅はプルダウン操作のたびに綺麗にフィット
  するため実害は小さいが、完全に解決するには生JavaScriptイベントを扱う
  カスタムコンポーネントの開発が必要
- ホバー情報ボックスをチャート枠外の固定位置に表示することはできない
  （Plotlyの標準機能はカーソル追従のみで、位置決めは自動配置。固定位置に
  出すには生JavaScriptによるカスタムコンポーネントが必要）
- 移動平均線上にホバー位置を示す丸印（Yahoo Financeのチャート等でよく見る
  マーカー）は表示できない。Plotly標準機能では線トレースに対して
  ホバー時の自動マーカー描画をサポートしておらず、実現には`plotly_hover`
  イベントを監視するカスタムJavaScriptが必要
- 縦の点線を出来高サブプロットまで完全に伸ばすことはできない（Streamlit
  同梱のPlotly.jsのバージョンによる制限と考えられる）

# 5. 売買銘柄タブ（トレード記録）

`database/trade_repository.py`（`trades`テーブル）で永続化。

- 日足・週足・月足を切り替えるラジオボタンは無く、区別は表内の「時間足」列
  のみで行う（データの保存自体は引き続きtimeframe列で分けて保持する）
- 「保有中」（決算株価が未入力）・「決算済み」（決算株価入力済み）の
  2セクションに分けて表示する（`_render_trades_section`）。決算株価を
  後から入力する（またはいったん入力した決算株価を空欄に戻す）と、
  対応するセクション間で表示が自動的に切り替わる。表・編集ロジック自体は
  共通の`_render_trade_table`をどちらのセクションからも呼ぶ
  - 「保有中」はグルーピングせず1つの表で表示する（未決済トレードは
    損益が無く、月間・年間の集計対象にもならないため）
  - 「決算済み」は年→月にグルーピングして表示する（`service/trade_service.py`の
    `group_by_year_and_month`）。月間損益・年間損益を表示する
  - 合計損益・削除・監視銘柄への移動は、保有中/決算済みを問わず一括で扱う
- 全期間の損益合計は保有中・決算済み両方を合わせたトレード全体から計算する
  （`total_pnl`。未決済トレードの損益はNoneのため集計対象外）
- 損益計算（`calculate_pnl`）: ロングは`(決算株価-購入株価)×株数`、
  ショートは`(購入株価-決算株価)×株数`。決算株価が無い（未決済）トレードは
  損益計算・集計の対象外。この関数は常に**税引前（グロス）**の額を返す
  （2026-08-28改訂。以前は個別トレードごとに課税していたが、下記の通り
  合計額への一括課税方式に変更したため）
  - 表内の「損益」列・月間損益は税引前（グロス）で表示する
  - 譲渡益課税（特定口座・源泉徴収ありを想定、
    `config.config.CAPITAL_GAINS_TAX_RATE` = 20.315%）は**個別のトレードでは
    なく、暦年（trade_dateの年）で損益通算した合計額に対して1回だけ**
    計算する（`service.trade_service._net_after_tax_pnl`、2026-08-28変更。
    特定口座の損益通算・源泉徴収の実務に合わせた。年をまたいだ損益通算は
    行わない）。年間損益・全期間の損益合計は、この年単位の税引後の額を
    使う（全期間の損益合計は各年の税引後の額を単純合算する）。その年の
    合計がマイナスなら非課税（税還付は計算しない）
    - NISA口座での取引は常に非課税（2026-08-26追加）。表内の「NISA」列
      （`st.column_config.CheckboxColumn`）にチェックを入れると、その
      トレードの損益は上記の損益通算の対象から除外し、税引前の額のまま
      年間損益・全期間の損益合計に加算する（`trades.is_nisa`列、
      `database.trade_repository`）。デフォルトは非チェック（特定口座
      扱い）。「NISA」列は決算済みセクション（下記read_only）でも
      例外的に編集可能。個別の「損益」列表示自体には影響しない
      （常にグロス表示のため）
- 損益がマイナスの行は行全体を赤字で表示する（2026-08-25追加、太字を廃止し
  行全体に適用するよう改訂。`ui.dashboard._style_negative_pnl_red()`、
  pandas Styler経由）。`st.data_editor`はStyler由来の見た目を編集不可の列に
  のみ適用するため、行全体を漏れなく赤字にするには行全体をdisabledにする
  必要がある。そのため決算済みセクションの表は**「表示」「NISA」「決済日」
  以外編集不可**にした（2026-08-26改訂。以前は購入株価・決算株価・株数・
  時間足を編集できたが、損益マイナス行を全列赤字にするための制約上、
  決算済み全体を対象に編集を無効化した。取引日・価格・株数・時間足を
  修正したい場合は対象銘柄を選択し「保有中に移動」してから保有中セクション
  （引き続き編集可能）で修正する。NISA区分・決済日だけは決算済みでも
  例外的に編集可能にしている。NISA区分は税区分の後からの修正がよくある
  ため、決済日は決済日の記録が無い既存の決算済みトレードへの後入力の
  ニーズがあるため）。保有中セクションは損益が常にNone（マイナスに
  なり得ない）なのでこの制約の対象外で、従来通り編集できる
- 表内の並び順は取引日の昇順（古い順）。新しく追加した銘柄ほど下に来る
  （`database.trade_repository.get_all_trades()`のSQL、2026-08-25改訂。
  以前は降順＝新しい順だった）。「保有中」・「決算済み」各月の一覧いずれも
  この順序を引き継ぐ（年→月のグループ自体は新しい方が上のまま。並び順を
  変えたのはグループ内の銘柄の順序のみ）
- 保有中セクションでは、取引日・購入株価・決算株価・決済日・株数・時間足・
  NISA区分を直接編集できる（`st.data_editor`）。時間足は`SelectboxColumn`
  （日足/週足/月足）で、時間足を間違えて登録した場合にここで修正できる。
  取引日・決済日は`st.column_config.DateColumn`（2026-08-26追加。取引日は
  同日追加、登録間違いの修正用）でカレンダーピッカーから入力できる。
  DataFrameの当該列を`pd.to_datetime()`で明示的にdatetime64へ変換してから
  渡している（2026-08-28追加。object dtype（date/Noneの混在）のままだと
  カレンダーUIが出ずテキスト直接入力扱いになる環境があったため）。決済日は
  決算株価を入力したときの実際の決済（受け渡し）日を記録するための任意項目
  （`trades.exit_date`列）で、決算株価が空欄に戻ると自動的にクリアされる
  （「保有中に移動」ボタン経由）
- 列の並び順は 表示・コード・銘柄名・方向・NISA・時間足・取引日・決済日・
  購入株価・決算株価・株数・損益（2026-08-29改訂。決済日を決算株価の後ろ
  から取引日の直後へ移動）
- 「表示」「コード」「銘柄名」列は`st.column_config.Column(pinned=True)`で
  固定し、横スクロールしても常に表示されるようにしている（2026-08-29追加。
  「方向」以降の列は横スクロールで隠れる。保有中・決算済み両セクション共通）
  - この固定表示はブラウザの表示幅が十分に広い場合のみ有効になる
  （glide-data-gridの仕様。実測ではサイドバー表示中の画面幅が900px程度
  では固定が効かず全列が一緒にスクロールしてしまい、1400px程度あれば
  正しく固定される）。スマホ等の狭い画面幅では固定されない点に注意
- 決算済みセクションには税計算方法の説明キャプションを表示していたが、
  各列のヘルプツールチップ（列ヘッダーの補足アイコン）で個別に説明して
  いるため2026-08-29に削除した
- 銘柄の選択はスキャンタブの候補一覧（3.1節）と同じ考え方で、表の先頭列
  「表示」チェックボックス（`st.column_config.CheckboxColumn`）で行う。
  チェックした銘柄の株価チャートを、表より上（スキャンタブの銘柄詳細と
  同じ位置）に表示し、「株価チャート」の見出しまで自動でスクロールする
  （4.2節の`_render_chart_block`、`key_prefix="trades"`。スクロールは3.1節の
  `_render_scroll_if_needed()`と共通）。
  削除・移動先を誤って選ばないよう、操作前にチャートで確認できるようにする
  ため。「表示」はDBに保存しないUI専用の選択状態で、
  `st.session_state["trades_chart_focus_id"]`で管理する
  - `st.data_editor`は、選択（focus_id）が変わるたびに`key`を再生成して
    ウィジェットを作り直している。同じ`key`のまま「表示」列の値だけを
    プログラム側で更新しようとすると、ウィジェット内部の編集状態が
    優先されてチェック状態が正しく切り替わらないため
- 何も選択していない状態では、削除・移動の代わりに選択を促すヒントを表示する
- 選択した取引が保有中か決算済みかで、操作できるボタンが異なる
  - **保有中**を選択: 「選択した取引を削除」「選択した取引を監視銘柄に移動」の
    いずれかを実行できる。「監視銘柄に移動」は登録を間違えた場合の修正用
    （例: 本来は監視銘柄として登録するつもりだった銘柄を誤って売買銘柄に
    登録してしまった場合）。選択した取引を削除したうえで、同じ銘柄・方向・
    時間足で監視銘柄に登録し直す（6.1節の重複登録防止チェックは行わない。
    対象の取引自体を削除したうえでの移動のため）
  - **決算済み**を選択: 「選択した取引を保有中に移動」のみを実行できる
    （削除ボタンは出さない。確定した損益の記録を誤って削除してしまう
    事故を防ぐため）。決算株価の入力を誤った場合の修正用で、取引自体は
    削除せず決算株価をクリアするだけ（`update_trade(..., exit_price=None)`）。
    これにより表示が保有中セクションへ自動的に移る

# 6. 監視銘柄タブ

`database/watchlist_repository.py`（`watchlist`テーブル）で永続化。

- 売買銘柄タブと同様、日足・週足・月足を切り替えるラジオボタンは無く、
  区別は表内の「時間足」列のみで行う
- 時間足は`st.data_editor`の`SelectboxColumn`で直接編集でき、登録間違いを
  後から修正できる（`database.watchlist_repository.update_watchlist_timeframe`）
- 「優先監視銘柄」・「監視銘柄」の2セクションに分けて表示する
  （2026-08-25追加、`_render_watchlist_section`が
  `watchlist.priority`列（0=通常/1=優先）で振り分ける）。優先監視銘柄が
  上、監視銘柄が下。振り分けは監視銘柄タブに追加した**後**に行う操作で、
  追加時点では常に通常（priority=0）として登録される。表・編集ロジック
  自体は共通の`_render_watchlist_table`をどちらのセクションからも呼ぶ
- 表内の並び順は追加日の昇順（古い順）。新しく追加した銘柄ほど下に来る
  （`database.watchlist_repository.get_all_watchlist_stocks()`のSQL、
  2026-08-25改訂。以前は降順＝新しい順だった。売買銘柄タブと同じ考え方）。
  この順序は優先監視銘柄・監視銘柄それぞれのセクション内で独立に適用される
- 売買銘柄タブと同様、表の先頭列「表示」チェックボックスで選んだ銘柄の
  チャートを表より上に表示し、「株価チャート」の見出しまで自動でスクロールする
  （4.2節の`_render_chart_block`、`key_prefix="watchlist"`、選択状態は
  `st.session_state["watchlist_chart_focus_id"]`でタブ全体に1つだけ持つため、
  どちらのセクションで選択してもチャートは1箇所に表示される）
- 何も選択していない状態では、削除・移動の代わりに選択を促すヒントを表示する
- 銘柄を選択すると、以下を実行できる
  - 「選択した監視銘柄を削除」
  - 優先/通常の振り分けボタン（2026-08-25追加）: 選択中の銘柄が通常なら
    「選択した監視銘柄を優先監視銘柄に追加」、優先ならボタンの表示が
    「選択した監視銘柄を優先から外す」に切り替わる
    （`database.watchlist_repository.update_watchlist_priority`）。
    どちらのセクションの銘柄を選択しても、もう一方へ移動できる
  - 下のフォーム（取引日・購入株価・株数・決算株価）に入力して
    「売買銘柄に移動」。その監視銘柄を削除したうえで、同じ銘柄・方向・
    時間足で売買銘柄に登録する（購入株価等はスキャンタブの候補一覧と
    違って自動入力されないため、手動で入力する）

## 6.1 売買銘柄との重複登録防止

同じ銘柄コードを売買銘柄・監視銘柄の両方に登録できないようにする
（方向・時間足は問わず、コードのみで判定）。

- **監視銘柄への追加**（スキャンタブから）: その銘柄コードに保有中（未決済、
  `exit_price IS NULL`）の売買銘柄が既にあれば、追加を拒否してエラー表示する
  （`database.trade_repository.has_open_trade`）。決算済みのトレードは
  対象外（再度監視対象にしてよい）
- **売買銘柄への追加**（スキャンタブから）: 追加と同時に、同じ銘柄コードの
  監視銘柄があれば自動的に削除する
  （`database.watchlist_repository.delete_watchlist_stocks_by_code`）。
  「監視 → 保有」への卒業とみなし、手動での削除操作は不要にしている
- 上記2つのチェックは、5章・6章の「削除して登録し直す」移動操作には適用しない
  （対象そのものを削除したうえでの移動のため、重複は発生しない）

# 7. データモデル

## trades

| 列 | 内容 |
|---|---|
| id | 主キー |
| code, company_name, direction | 銘柄コード・銘柄名・方向（long/short） |
| timeframe | 登録時の時間足（"daily" \| "weekly" \| "monthly"）。デフォルト"daily" |
| trade_date | 取引日（"YYYY-MM-DD"） |
| entry_price, exit_price, quantity | 購入株価・決算株価（NULL=未決済）・株数 |
| created_at | 登録日時 |

## watchlist

| 列 | 内容 |
|---|---|
| id | 主キー |
| code, company_name, direction | 銘柄コード・銘柄名・方向 |
| timeframe | 登録時の時間足（"daily" \| "weekly" \| "monthly"）。デフォルト"daily" |
| added_date | 追加日（"YYYY-MM-DD"） |
| created_at | 登録日時 |

timeframe列は後から追加したため、`create_table()`内で
`ALTER TABLE ... ADD COLUMN timeframe TEXT DEFAULT 'daily'`による
マイグレーションも行う（既存データは全て日足として扱う）。
`ui/dashboard.py`が起動のたびに`create_trades_table()`/
`create_watchlist_table()`を呼ぶため、既存DBでも自動的に反映される。
